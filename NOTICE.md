## Origin

Zenlygram for Android is a modified version of Telegram for Android 13.2.1 (7291)
(https://github.com/DrKLO/Telegram, commit `7be672ead283d022812d75c729d3a04dd4c2a2c6`).
The code inherited from it remains under the copyright of its authors.

Zenlygram's own code (Secret Vault, Chat Lock, Tasks, the history of edited and deleted messages, the settings
pages, the account link and the client of the Zenlygram server) is mainly under
`TMessagesProj/src/main/java/org/telegram/zenlygram/` and
`TMessagesProj/src/main/java/org/telegram/messenger/zenlygram/`, with smaller pieces in the upstream files it
touches. Much of it follows the behaviour of Zenlygram for iOS (https://github.com/Zenlygram-org/zenlygram-ios), which is derived from Swiftgram
and Telegram for iOS; comments name the iOS types it corresponds to. The icon resources are generated from
files of that iOS project by the scripts under `Tools/zenlygram/icons/`. The three `strings_zenlygram.xml` files
were generated by `Tools/zenlygram/ios_strings_to_android.py` from that project's string table as it was on
2026-10-29 (their first line names the SHA-256 of the input). That revision is older than the published iOS
commits: on their string table the generator stops with a name collision until its `KEY_RENAMES` are extended.
The XML files in this repository are complete and are what the build compiles.

[UPSTREAM-CHANGES.txt](UPSTREAM-CHANGES.txt) lists every file of this repository that differs from that
Telegram for Android commit (A = added, M = modified, D = deleted: 842 added, 141 modified,
15 deleted), as required by section 2(a) of the licence. Zenlygram's changes for Android were made
in 2026: first on top of Telegram for Android 12.10.6 (published 2026-09-30), from November 2026 on top of
13.2.1. The changes in each commit of this repository end no later than the date of that commit.

## What this repository contains

This repository is published at https://github.com/Zenlygram-org/zenlygram-android-source.
Each commit on its branch `main` is the source of one published build and carries the tag
`android/<version>-<build>`. It is an export of the project's private development tree at the commit that build
was made from. Every source file and every build script is published unchanged; the files listed further
down that differ are not inputs of the build. Three inputs of a published build are in no tree: the Telegram API
pair, the signing key, and the Firebase configuration, which the build puts in place of the placeholder files
`TMessagesProj/google-services.json` and `TMessagesProj_App/google-services.json`.

| Version | Build (versionCode) | Tag | Built (UTC) |
|---|---|---|---|
| 13.2.1.1 | 73041 | `android/13.2.1.1-73041` | 2026-11-17 |

Both are built with `-PZG_LENTA=false` from the same commit: the Google Play bundle (`bundleAfat`, the versionCode
ending in 1) and the side-load APK (`afat`, ending in 9). The build row above names the one that was distributed.

Left out are files that are not part of the shipped app:

- the sources and tests of an unreleased feature: `TMessagesProj/src/lenta/` and
  `TMessagesProj/src/lentaTest/` (243 files) and its development helper
  `Tools/zenlygram/lenta-dev-login.sh`. The Gradle property `ZG_LENTA` decides whether that feature is
  compiled (left unset, it is on in debug builds and off in every other build type). Every published build is
  made with `-PZG_LENTA=false`, which compiles the one-file stand-in `TMessagesProj/src/lentaStub/` instead, so
  none of these sources is in the app;
- the project's internal documents and store tooling: `ZENLYGRAM.md`, `docs/zenlygram-cloud-android.md`,
  everything under `Tools/zenlygram/play/` (4 files) and the workflow
  `.github/workflows/zenlygram-android.yml`.

Files that differ from the development tree (none of them is compiled into the app):

- `NOTICE.md` and `UPSTREAM-CHANGES.txt` are written for this repository;
- `README.md`: the paragraph that introduces Zenlygram points to this notice instead of the internal guide.

Comments and messages in the published files may name documents and tools of the development tree that are
not part of this repository. A build with that feature turned on (`-PZG_LENTA=true`, or a debug build without
`-PZG_LENTA=false`) needs the unpublished sources and does not work from this repository; the published builds
do not need them.

## Building

1. Get the submodules: `git submodule update --init --recursive`.
2. Use your own Telegram API pair (https://my.telegram.org, "API development tools") as the Gradle properties
   `ZG_API_ID` and `ZG_API_HASH` (for example in `~/.gradle/gradle.properties`, or `-PZG_API_ID=… -PZG_API_HASH=…`).
   `TMessagesProj/zenlygram-identity.gradle` describes them; a release build stops without them.
3. `./gradlew :TMessagesProj_App:assembleAfatRelease -PZG_LENTA=false` builds the side-load APK
   (`TMessagesProj_App/build/outputs/apk/afat/release/app.apk`);
   `./gradlew :TMessagesProj_App:bundleBundleAfatRelease -PZG_LENTA=false` builds the Google Play bundle.
   Pass `-PZG_LENTA=false` to every build and test run, debug ones included: without it a debug build turns the
   unreleased feature on, and its sources are not in this repository.
   `TMessagesProj/build.gradle` names the Android SDK platform, the build tools and the NDK version; the Java
   runtime bundled with a current Android Studio runs the build.
4. Signing: without the `ZG_UPLOAD_*` properties of `TMessagesProj_App/build.gradle` a release build is signed
   with the public test key of the upstream project (`TMessagesProj/config/release.keystore`). An APK signed with
   another key does not install over a published Zenlygram build.
5. Push notifications need your own Firebase project: the committed `google-services.json` files are
   placeholders.
6. The values of the data operator named by the consent text are in `TMessagesProj/zenlygram-cloud.gradle`. A
   build that talks to the Zenlygram server must keep them: the server refuses a consent whose text names
   another operator. A build of your own for another server sets its own.

A build made this way differs from the published one in the signature, in the API pair and in the Firebase
configuration.
